| 能力 | 输入→输出 | 实测耗时 | 实测峰值显存 | 依赖 |

| 图生视频（成品镜头） | 起点图 → 121 帧 @24fps（5.0 s） | **722 s** | 6.91 GiB | 同上（该次 CLIP 在 CPU；GPU 版约 687 s 为推算） |
| 补帧 2× | 17 帧 → **33 帧** | **1.8–3.1 s** | **0.92 GiB**（单独跑） | `rife_v4.26_heavy` |
| 训练一个新角色 LoRA | 24 张图 + 24 个 txt → 67.8 MB LoRA | **7.5 min**（960 步） | 3.2 GiB | OneTrainer 无界面 |
| 造训练集（合成角色图集） | 提示词 → 24 张 512×512 | **49 s** | ~2.2 GiB | SD1.5 |

**换算规律（用于排产）**：
- 四个实测点（17/29/57/121 帧 = 75 / 155 / 382 / 722 s）：**边际约 8 s GPU / 输出帧**，折算每 1 秒 720p 成片的 GPU 成本在 **106–161 s** 之间（0.7 s 镜头 106、1.2 s 128、2.4 s 161、5 s 143）。**没有"越长越便宜"的规模效应**，所以动漫剪辑本来就常用的 1.5–2.5 s 短切，就是本机最直接的提速手段，比任何蒸馏都实在。
- 补帧 ≈ **0.1 秒/帧、0.9 GiB**，几乎免费。帧数关系是 **(N−1)×multiplier + 1**，不是 2N（17→33、29→57）。
- ⚠️ **"生成一半帧数再 RIFE 补回原时长"不能省时间**：实测会把动作变成慢动作/动作量不足（见 §3.6）。RIFE 的正确用法见 §5.2-C。

## 3. 测试过程（原始记录）

### 3.1 VAE 解码 A/B（决定生死的实验）
同一条 17 帧 720p 链路，20 步 / CFG 5 / `uni_pc` / `simple` / `ModelSamplingSD3 shift=8`：

| 配置 | 整链耗时 | 峰值 |
|---|---|---|
| 核心 `VAEDecode`（官方模板默认） | 采样 74 s，**解码 >40 min 未完成**，且不响应 `/interrupt` 与删除队列项 | 7.82 GiB |
| `VAEDecodeTiled`(512/32/32/8) + CLIP `device=default` | **75.2 s** | 7.25 GiB |
| `VAEDecodeTiled` + CLIP `device=cpu` | 110.2 s | 6.81 GiB |

结论：tiled 解码是**强制项**；文本编码器留 GPU。CLIP 放 CPU 的代价是固定 ~35 s（与帧数无关），17 帧时占 32%，121 帧只占 5%。

### 3.2 121 帧成品
`VAEDecodeTiled` + CLIP CPU：**722.0 s（12 分钟）/ 6.91 GiB**，产物 `output\wanbench\FULL_121f_720p_00001_.mp4`（1280×704, 5.04 s, 24fps）。按 §3.1 的固定 CLIP 开销推算，CLIP 放 GPU 约 **687 s**（未单独实测）。

### 3.3 端到端串联（LoRA → 分镜 → 视频）
1. SD1.5 合成 24 张同角色图集（49 s）→ `E:\ComfyUI\dataset\saki_chan`
2. OneTrainer 训练 40 epoch（7.5 min，2.2 步/秒，3.2 GiB）→ `saki_chan_lora.safetensors`
3. LoRA 挂 ComfyUI，出 4 个机位 1280×704（7.2–8.8 s/张）：肖像 / 走廊全身 / 低角度 / 咖啡馆 —— **脸、发色、制服、领结全部一致**
4. 走廊那张作起点图 → Wan 17 帧：**71.1 s / 7.14 GiB** → `output\manhua\ep01_walk_17f_00001_.mp4`

### 3.4 三条支路补测（对 Desktop 官方后端）
- ControlNet canny（strength 0.8 / end 0.8）：**18.6 s / 4.18 GiB** —— 走廊透视与人物站姿完全锁住，提示词把窗外天空换成黄昏。
- IPAdapter PLUS（weight 0.9）：**12.9 s / 6.55 GiB** —— 迁移了画风与构图，**没迁移身份**（参考图是远景全身）。
- RIFE ×2（17→**33** 帧）：**2.6 s**；当时报的 4.25 GiB 是 Wan 权重仍驻留所致，§3.6 单独测得 **3.1 s / 0.92 GiB**。

### 3.5 一次无效数据的教训
最初测得 3.74 s/步（采样 74 s）是在 **IPAdapter 2.5 GB 正在下载 + OneTrainer 正在 pip 安装**时采的。D 盘同时承担模型文件与下载落盘，USB4 单链路被抢占，**数字被显著污染**。此后所有基准都在"无下载/无安装"状态下重采。

### 3.6 半帧 + RIFE vs 原生 24fps（公平 A/B，已做完）

**设计**：同一张起点图（`hallway_00001_.png`）、同一提示词、同一 seed=42、同一采样器，两条路都产出**恰好 57 帧 @24fps = 2.375 s**：
- **A 原生**：`length=57` @24fps
- **B 半密度**：`length=29` @12fps → `FrameInterpolate ×2` → 57 帧 @24fps（(29−1)×2+1 = 57，帧数与时长精确对齐）

| 臂 | GPU 耗时 | 峰值显存 | 产物 |
|---|---|---|---|
| A 原生 57 帧 | **381.6 s** | 7.21 GiB | `output\ab\native57_00001_.mp4` |
| B 生成 29 帧 | **155.4 s** | 7.15 GiB | `output\ab\half29_00001_.mp4` |
| B 补帧 ×2 | **3.1 s** | **0.92 GiB** | `output\ab\half29_rife57_00001_.mp4` |

**结论：B 只用 41% 的 GPU 时间（158.5 s vs 381.6 s，快 2.41×），但代价不是免费的——动作量明显变小，等于慢动作。**

客观指标（cv2 逐帧，57 帧）：

| 指标 | A 原生 | B 半帧+RIFE | 读法 |
|---|---|---|---|
| 相邻帧平均差 | 0.01629 | 0.01044（0.64×） | B 每帧变化更小 |
| 差分剖面变异系数 CV | 0.2783 | 0.2564 | 平滑度相当，B 略匀 |
| 奇偶步不对称（judder） | **0.059** | **0.259** | B 的步长呈"大-小-大-小"交替，即轻微顿挫；A 基本均匀 |
| 清晰度（Laplacian 方差，全帧） | 1218 | 1299 | 整体锐度持平 |
| 插值帧 / 原始帧清晰度比 | （对照 1.029） | **0.935** | 插值帧软 6.5% |
| 与"邻域线性均值"的残差（奇数位帧，0–255） | 3.18 | **1.46（0.459×）** | 插值帧**没有鬼影**，比模型自己的帧间抖动还平滑 |
| **人物表观面积 f56/f0** | **4.667×** | **1.670×** | ← 决定性：A 从远景推到半身，B 几乎没靠近（B 只做到 A 的 **36%**） |

目视（`view_grid.jpg` / `view_crop.jpg` / `view_resid.jpg`，由 `tools\ab_rife_visuals.py` 生成，指标落盘在同目录 `metrics.json`）：A 序列 f00 远景 → f40 半身 → f56 胸像特写；B 序列 f00 → f56 仍是全身远景。残差热图上 B 的插值帧只有细描边级别的高能区（正确的运动边缘插值特征），**没有出现"双影/重像"**，说明 RIFE 本身质量没问题——问题在"少生成一半帧"这件事本身。

**机理**：`Wan22ImageToVideoLatent.length` 决定的是**这段动作的故事时长**（N 帧按 24fps 播 = N/24 秒），不是"同一时长的采样密度"。所以 29 帧只装了 1.2 s 的动作，按 12fps 播到 2.4 s 就变成慢动作；模型并不会因为帧数少就把同样的动作做完。

**方法论教训**：第一版用"暗色主体像素高度"和"首末帧灰度均差"当动作量代理，两者都被前景立柱/储物柜污染（给出 1.061 vs 1.064、0.917 的假"等价"结论），是**目视才推翻的**。测动作量必须用主体色域分割（肤色+发色）后的**面积**，或直接看图。



## 4. 分析依据（为什么是这些结论）

1. **瓶颈是显存搬运，不是算力。** 12.6 GB 权重进 8 GB 卡 → 逐层流式；非 tiled 的 Wan VAE 解码要把整段时序张量铺开，触发持续换页 → 40 分钟不结束且不可中断。tiled（空间 512 + 时间 32 分块）把工作集压到卡内，同一条 17 帧链路 **75.2 s 跑完**（§3.1）。
2. **文本编码器不该省显存。** umt5 每条提示词只跑 2 次（正/负），放 CPU 换来的是固定 35 s 白等，而它腾出的显存对采样并无增益。
3. **5B 而非 14B。** 5B 用 `wan2.2_vae`（4×16×16 + patchify 2×2），14B 用 `wan_2.1_vae`（8×8×4）；同为 720p 时 14B 的 token 数约 4 倍、注意力 FLOPs 约 16 倍，再加 27B 权重 → 本机不可行。
4. **不要期待 4 步蒸馏。** `Wan2.2-Distill-Loras` / `Lightning` / `Distill-Models` 均为 **A14B only**；5B 无 distill LoRA，只能维持 ~20 步 / CFG 5。真正的加速手段只有**减少成片时长（帧数）**和**降分辨率**——RIFE 不能用来偷时长（§3.6），它只提升顺滑度。
5. **角色一致性靠 LoRA，不靠 IPAdapter。** 实测 IPAdapter 只搬风格/构图；身份稳定必须由 24–40 张同角色图集训出 LoRA（合成图集同样有效，因为基座与出图用同一个 checkpoint）。
6. **训练与视频任务不能同卡并行。** 训练 3.2 GiB + Wan 7.1 GiB > 8 GiB；且并行会像 §3.5 那样污染计时。
7. **`length` 是故事时长，不是采样密度**（§3.6 实测）。N 帧 = N/24 秒的动作，因此"少生成一半帧再补回来"必然得到慢动作。想省 GPU 只能减少**成片时长**或分辨率，不能靠补帧偷时长。
8. **RIFE 在本机的定位是质量工具，不是产能工具**：3.1 s / 0.92 GiB，几乎免费，且插值帧残差只有原生帧间抖动的 **0.459×**（无鬼影）。它适合做 48fps 顺滑版、氛围镜头的刻意慢动作，不适合冒充产能。
9. **每成片秒的 GPU 成本没有规模效应**（0.7 s 镜头 106 s/成片秒、1.2 s→128、2.4 s→161、5.0 s→143）。动漫剪辑本来就多用 1.5–2.5 s 短切，所以**把镜头切短**是比任何蒸馏都实在的提速手段：2.4 s 一镜 6.4 分钟，5 s 一镜 12 分钟。

## 5. 怎么做

### 5.1 API 调用范式（程序驱动）

```python
import json, urllib.request
API = "http://127.0.0.1:8188"

def submit(graph_api_format):          # 注意：body 必须是 {"prompt": graph}
    return json.load(_req("/prompt", {"prompt": graph_api_format}))["prompt_id"]

def _req(path, payload):               # /free 与 /interrupt 返回空 body，必须容错
    req = urllib.request.Request(API + path, data=json.dumps(payload).encode(),
                                 headers={"Content-Type": "application/json"})
    return urllib.request.urlopen(req, timeout=60)

def wait(pid):
    import time
    while True:
        time.sleep(3)
        h = json.load(urllib.request.urlopen(API + f"/history/{pid}", timeout=60))
        if pid in h:
            e = h[pid]
            if e["status"].get("status_str") == "error":
                for m in e["status"].get("messages", []):
                    if m[0] == "execution_error":
                        raise RuntimeError(f"{m[1]['node_type']}: {m[1]['exception_message']}")
                raise RuntimeError(json.dumps(e["status"]))
            return e

def free_vram():                        # 训练/大任务前释放显存，不要杀后端进程
    _req("/free", {"unload_models": True, "free_memory": True}).read()

def elapsed(e):                         # 本版本 history 顶层没有起止时间戳
    s = {m[0]: m[1]["timestamp"] for m in e["status"]["messages"]
         if isinstance(m, list) and isinstance(m[1], dict)}
    return (s["execution_success"] - s["execution_start"]) / 1000.0
```

要点（都是踩过的坑）：
- **API 格式 ≠ 界面格式**。界面 JSON 是 LiteGraph（`nodes[]` + `links[]` + `widgets_values` 顺序），API 是 `{node_id: {"class_type":..., "inputs": {...}}}`。界面里 widget 的顺序 = 该节点**未连线**输入的出现顺序。
- `links` 里的元素是 `[id, src_node, src_slot, dst_node, dst_slot, type]`。
- 产物在 `history[pid]["outputs"][<node_id>]` 下按**节点 id 分键**；图片是 `["images"][0]`，**视频也在 `["images"]` 里（不是 `["videos"]`）**，用 `filename` 以 `.mp4/.webm` 结尾 + `type=="output"` 过滤。每项自带 `metadata = {width, height, fps, duration, frame_count}`，**排产核对帧数不用再解 mp4**。
- `LoadVideo` 节点也会把**输入**视频写进 `outputs["images"]`（`type=="input"`），别当成产物。
- 界面 JSON 里若含中文，读写必须显式 `encoding="utf-8"`；本项目工作流的负面提示词曾因 GBK 转码变成不可恢复乱码（已替换为英文模板，备份 `*.bak-mojibake-negative`）。
- 新克隆的节点包、新增的模型**类别**要 Stop→Start 才出现；新放进已扫描类别的文件不用重启。
- 部分下载的模型**已经会出现在下拉里**，跑起来才在 safetensors 头处报错 —— 排产前先核对字节数。


**帧数公式：输出 = (N−1) × multiplier + 1**（17→33、29→57、61→121）。所以 `CreateVideo.fps` 必须设为**原 fps × multiplier** 才能保持时长不变。

三种正确用法（成本都是 3 s / 0.9 GiB 量级）：

| 用法 | 做法 | 结果 |
|---|---|---|
| **顺滑升级（推荐）** | 原生 N 帧 @24fps → ×2 → @**48fps** | 时长与速度不变，运动更连续；48fps 交付 |
| **刻意慢动作/氛围镜头** | `length=N` 生成 → @**12fps** 存 → ×2 → @24fps | 时长 2×，动作变慢（实测动作量只有原生同长的 36%，见 §3.6）——这是风格，不是省产能 |
| ~~冒充产能~~ | ~~半帧 + 补帧当原生用~~ | **不成立**，见上面第二行的速度副作用 |

## 6. 结论与推荐生产参数

**这套流水线能做的**：固定角色、多机位、带运镜的动漫短剧镜头，全部本地生成，无云端依赖、无 API 费用。

单镜头推荐配方（性价比最高）：
1. 分镜图：SD1.5 + 角色 LoRA，1280×704，22 步 CFG 7 euler/normal → **~8 s/张**
2. 需要复用机位/动作时：加 `control_v11p_sd15_canny`（strength 0.8，end 0.8）→ **+10 s**
3. 动画：Wan2.2 5B fp8，20 步 CFG 5 `uni_pc/simple`，`ModelSamplingSD3 shift=8`，**`VAEDecodeTiled 512/32/32/8`**，CLIP `device=default`
4. **时长策略（已实测，见 §3.6）**：
   - 草稿/试运动：`length=17` → 71 s
   - 成片主力：`length=29`（1.2 s，155 s）或 `length=57`（2.4 s，382 s）——动漫剪辑本来就以 1.5–2.5 s 短切为主
   - 长镜：`length=121`（5 s，≈12 min）只在确有必要时用
   - **不要**用"半帧 + RIFE"换时长：那会把动作变成慢动作（实测动作量只剩 36%）
5. RIFE 的正当用途：① 原生 N 帧 @24fps → ×2 → **48fps** 顺滑版（+3 s / 0.9 GiB，速度不变）；② 刻意慢动作的氛围镜头
6. 全程**不要**同时跑 OneTrainer 与 Wan

**一集 20 个镜头估算**：分镜 20×8 s ≈ 3 min + 动画按平均 2 s/镜（`length=49` ≈ 320 s，由 29/57 帧两点线性外推，8.1 s/帧）× 20 ≈ **1.8 小时 GPU**；若都用 5 s 长镜则是 4 小时。新角色每个另加 8 min 训练。

## 8. 故障排查

| 症状 | 根因 | 处置 |
|---|---|---|
| 视频解码卡死几十分钟，`/interrupt`、删队列都无效 | 非 tiled 的 Wan VAE 解码 + DynamicVRAM 换页 | 在 Desktop 里 Stop→Start 后端（**不要**从命令行杀它管理的进程）；工作流改 `VAEDecodeTiled` |
| 补帧后视频变 2 倍长 / 动作变慢 | 误以为 `length` 只是采样密度；实际 N 帧 = N/24 秒动作 | 保持时长不变时 `CreateVideo.fps` 用**原 fps × multiplier**（见 §5.2-C） |
| `json.load` 在 `POST /free` / `/interrupt` 后抛 `Expecting value` | 这两个端点返回 **200 + 空 body** | 先 `.read()`，空则返回 `{}` |
| 视频产物在 `outputs[id]["videos"]` 取不到 | `SaveVideo` 把结果放在 **`["images"]`**，`type=="output"` | 按扩展名 + `type` 过滤；`metadata.frame_count` 可直接核对帧数 |
| `IPAdapter model not found.` / 下拉为空 | Desktop 的 `inst-*.yaml` 带 `is_default: true`，把 `ipadapter` 这类**非核心类别**整条指向 `ComfyUI-Shared\models\ipadapter`，实例目录里的文件看不见 | 硬链接到 `Shared\models\ipadapter\` |
| `received_type(VIDEO) mismatch input_type(IMAGE)` | `LoadVideo` 只输出 VIDEO | 中间插 `GetVideoComponents` |
| `httpx.InvalidURL: Invalid port: ':1]'` | 系统 `NO_PROXY` 含 `[::1]` | 进程内覆盖 `NO_PROXY=127.0.0.1,localhost` |
